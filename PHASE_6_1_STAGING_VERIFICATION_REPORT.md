## 4. Backup and restore rehearsal

**PASS — synthetic logical round trip only.** Used native `pg_dump` / `pg_restore` 16.2 against an isolated PostgreSQL 16.2 cluster. Used two distinct DBs: source `shopbd_release_source`, destination `shopbd_security_test`. The source was built by applying all six SQL migration files with `psql -X -v ON_ERROR_STOP=1 -f`, then inserting a synthetic product and FK-linked variant. This was separate from the failed native attempt. The archive was 61,178 bytes; `sha256sum --check` returned `release.dump: OK`; `pg_restore --list` read the TOC. A single-transaction restore into an empty destination took **135 ms** around `pg_restore` only, excluding data extraction, transfer, provisioning, role recovery and validation; this is not a staging RTO/RPO. Sorted source/destination catalog output matched (columns/types/defaults/nullability, constraints and validation, indexes, triggers, fixture); restored counts were **25 public tables, 53 constraints, 74 indexes**. `_prisma_migrations` was absent on both sides, as expected for SQL replay. All three DB suites ran on the restored destination, not on the source.

**BLOCKED — native-history restore.** The new CI sequence requires a native-migrated source, checks before/after no-op and after restore, then runs all DB suites against the isolated restore. Repeat with the SHA pinned in §2. For a manually reproduced test using compatible native clients and approved test-only connection services, the core commands are:

```sh
umask 077
pg_dump --dbname=service=shopbd_disposable_source -Fc --file=release.dump
sha256sum release.dump > release.sha256
sha256sum --check release.sha256
pg_restore --list release.dump > release.toc
# Independently confirm the destination already exists, is EMPTY and is isolated.
time pg_restore --dbname=service=shopbd_disposable_restore \
  --exit-on-error --single-transaction --no-owner --no-privileges release.dump
```

For the local/CI rehearsal, set `SHOPBD_RELEASE_DB_URL` to each disposable loopback URL in turn, diff the verifier's JSON, set `SHOPBD_SECURITY_TEST_DATABASE_URL` to the restored `shopbd_security_test`, then run the three DB commands in §5. Do not point these tests at a shared staging DB. Follow the [backup guide](DATABASE_BACKUP_RESTORE_GUIDE.md) for an authorized target-sized restore/PITR to a new isolated target. Record end-to-end elapsed time and recovered timestamp, verify least-privilege roles and grants separately, and include media availability, sampled totals and safe handling of revived sessions. No customer records or provider snapshots were used here.
