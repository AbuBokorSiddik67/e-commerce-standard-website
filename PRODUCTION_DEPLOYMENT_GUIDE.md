# ShopBD production deployment runbook

**Do not deploy from this guide until the release gates in the [Phase 6 report](PHASE_6_PRODUCTION_READINESS_REPORT.md) are cleared and the owner authorizes the release.** Use a separate staging domain, database, provider project and credentials. The application is a Node.js Next.js service, not a static export. A managed Next.js host such as Vercel plus managed PostgreSQL/Neon is a candidate, not a verified target.

## 1. Prepare the release

1. Select the reviewed commit. Use a patched Node 22 or 24 LTS within `package.json`'s range; `.nvmrc` records the tested 22.22.3 version. Match build and runtime target OS/architecture for Prisma, `pg`, and `sharp`.
2. On a clean runner: `npm ci`, `npm run db:generate`, `npm run lint`, `npm run typecheck`, `npm test`. Permit npm and the official Prisma engine downloads with integrity checks enabled. Do not copy development binaries into the release or bypass the native migration check. Run `.github/workflows/release-checks.yml` on the release revision; it uses an isolated PostgreSQL service, no store credentials.
3. Set up the stage and read the [environment checklist](PRODUCTION_ENVIRONMENT_CHECKLIST.md). Place secrets only in the host's secret manager. Configure build and runtime with the same build-target canonical origin; do not promote a staging build with the staging origin into production. Use a deploy preview protection policy, not `robots.txt`, to keep staging private.
4. Capture and rehearse transfer/restore as in the [database guide](DATABASE_BACKUP_RESTORE_GUIDE.md). Review dependency advisories and the [security audit](PRODUCTION_SECURITY_AUDIT.md) before any release sign-off.

## 2. Database and build

1. Configure TLS and least-privileged roles. `DATABASE_URL` is for runtime reads/writes; `DIRECT_URL` is for one migration job only. Never run the migration command in each app worker, the startup script, or a production build hook. Size the pool from the maximum concurrent processes, including rolling overlap; see the environment checklist.
2. Run `npm run db:deploy` and `npx --no-install prisma migrate status` in the migration job using the direct DB connection. Do not seed or run `migrate dev` in a deployed environment. If deployment fails, stop rollout and use the recovery decision tree in the database guide. Phase 6 adds no schema migration.
3. Build with `npm run build`. Build-time public settings can read PostgreSQL; build against the migrated target environment with a limited DB role and use the release smoke tests to verify rendered defaults are not substituting for missing settings. Do not inject runtime-only provider secrets into client/public environment variables.
4. Self-hosted: run `npm start -- --hostname 0.0.0.0 --port 3000` as a non-root worker behind the private ingress. Keep stdout/stderr captured, forward `SIGTERM` to the worker, stop routing traffic before signaling it, and allow the platform's drain grace period. No cron, seed or schema changes occur as part of startup. Platform-managed: select the Next.js preset, set Node and env controls, use the managed build/start and run a separate migration job. Rehearse the actual platform's startup validation; local `next start` success does not prove its serverless lifecycle.

## 3. HTTPS, cookies, assets and cache

1. Accept only the reviewed storefront host at ingress. Redirect HTTP and alternate hostnames to the HTTPS canonical host before reaching Node; reject arbitrary hosts. Overwrite `Host`, `X-Forwarded-Host` and `X-Forwarded-Proto` with validated values. Block direct public origin access. Set HSTS at the HTTPS edge once the domain is confirmed; do not blindly opt other subdomains into HSTS.
2. Do not apply a CDN “cache everything” rule. Bypass shared cache for all HTML/RSC, auth, Server Actions, API, checkout, account, admin, tracking and receipt traffic, and for any response with `Set-Cookie` or `private`/`no-store`. Preserve `X-Robots-Tag` and receipt/reset `Referrer-Policy`. Check authenticated and unauthorized requests from distinct clients from the deployed edge, not just Node.
3. Cache hashed `/_next/static/` assets and eligible public images only. Serve existing `/uploads/` and `/brand/` assets from the same release. Preserve `/_next/image` query variants and `Accept` negotiation. Use allowlisted HTTPS image hosts and durable UploadThing storage; no production filesystem fallback. A storage URL must be immutable/versioned if it will be edge-cached.
4. Public settings, active categories and sitemap source data have tags and a 120 s revalidation interval. For multiple workers, configure platform-supported shared Next.js tag invalidation or test and document bounded eventual consistency before launch. The CDN must not turn that interval into an unbounded HTML/XML stale cache. Never cache authoritative checkout or authentication state. Multi-instance self-hosting also needs consistent build artifacts/Server Action keys and a rolling strategy; verify mutations during rollout on staging.

## 4. Health, logs and provider checks

1. `/api/health/live` is process-only. `/api/health/ready` returns 200 for a usable settings-table read or 503 on DB failure. Neither is cached. Readiness is not proof of migration parity, credentials issuance, active COD zones, or provider delivery. Poll moderately, set a bounded probe timeout at ingress, and restrict probes to trusted infrastructure where possible.
2. Route only to healthy replicas. Alert on sustained readiness failure, 5xx, sharp login throttling growth, failed password mail, upload errors, and DB pool saturation or serialization retries. Track request/DB duration and status without payloads. Forward structured, sanitized application categories to your log destination; avoid logging address/order URL paths, headers, query strings, cookies or action bodies. Configure scrubbers and access/retention before enabling external monitoring. No external APM is configured here.
3. Complete the provider procedures in the environment checklist and run the [smoke checklist](PRODUCTION_SMOKE_TEST_CHECKLIST.md) against the deployed staging ingress. Match plan limits for request body size, timeout, regions and DB pool. Only after approval, roll out, watch health/errors/checkout and record the release owner and rollback revision.
