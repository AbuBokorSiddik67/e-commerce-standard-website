# ShopBD production environment checklist

1. **Isolation:** Create separate staging and live secret scopes, DBs, UploadThing apps, Resend senders, and public hosts. Never share scopes or use fixture credentials outside disposable tests. Keep `.env.example` as a blank-secret template. Set a supported patched Node LTS and don't enable development options on a deployed service.
2. **Runtime DB:** `DATABASE_URL` is a PostgreSQL URL with username and database name. Remote addresses require `sslmode=verify-full`. Use the platform CA or reviewed `sslrootcert` if necessary, and check TLS and DNS against the actual host. Plain local loopback is allowed for an isolated fixture/local trusted tunnel, not for a network hop. Do not disable TLS verification. A runtime client needs schema usage, table CRUD, and sequence access where applicable, but not migration/DB owner privileges. Verify each needed write flow as this role.
3. **Migration DB:** `DIRECT_URL` is the direct TLS connection with DDL rights for a single short-lived deploy job. Omit it from app instances. The Prisma config falls back to `DATABASE_URL` when `DIRECT_URL` is unset, so confirm the direct target explicitly before any migration run.
4. **Connection budget:** `DB_POOL_MAX` optional, 1–50, default 5 per Node process. `pg` connection/pool acquisition timeout is 5 seconds and idle timeout 30 seconds. Obtain the database/pooler limit and provider concurrency upper bound. Budget `pool max × peak processes across regions and old/new releases` plus DB jobs/operator/monitoring headroom; tune and verify saturation on staging. Do not assume Prisma URL `connection_limit` configures the `pg` adapter. Use a provider-supported pooler if needed and verify the serializable checkout transaction behavior through it.
5. **Auth and SEO:** `AUTH_URL` and `NEXT_PUBLIC_APP_URL` must be the same absolute HTTPS origin with no path, query, credentials or fragment. `AUTH_SECRET` is required; generate at least 32 random bytes in a secret manager and share across replicas of the same environment. Do not reuse or log it. Remove conflicting `NEXTAUTH_SECRET`/`NEXTAUTH_URL`. `AUTH_TRUST_HOST=true` only with the ingress controls in the deployment guide. Optional `AUTH_CLIENT_IP_HEADER`: configure one header that the ingress overwrites with one trusted client IP; never accept an arbitrary forwarded chain. Independent protected actions still confirm live DB sessions. There is no OAuth provider/redirect registration; verify the Credentials callback through the canonical `/api/auth/` routes and that checkout/login cookies are Secure and HttpOnly where expected.
6. **Resend:** Supply `RESEND_API_KEY` and `PASSWORD_RESET_FROM` together, with a least-privileged server key and verified sender/domain. Configure DKIM/SPF and policy as provided by the operator; disable tracking/link rewriting for recovery messages. From staging, request a reset for a synthetic registered address and an unknown address: public responses must match. Check that only the registered inbox gets a message, the URL has the canonical origin and fragment token, redemption works once, old sessions are invalid, repeat redemption fails and provider logs do not expose the link to unrelated operators. Without the pair, recovery fails closed without token issuance; this is **not** live recovery readiness. Contact support is a customer-controlled email draft, not a Resend submission. Verify the storefront contact address and actual inbox staffing.
7. **UploadThing/images:** Set `UPLOADTHING_TOKEN` from the staging app only. Leave `MEDIA_IMAGE_HOSTS` blank unless a reviewed exact HTTPS CDN host is needed (separate with commas). As admin, upload a small raster; verify re-encoded WebP provider object, allowed host, successful save, optimized image rendering on storefront and admin, stable versioned URL and cache separation. Exercise oversized/non-image and unauthorized denial; applications behind a restrictive request-body cap must test the actual 1–4 file limit or document the stricter edge cap. Confirm storage backup/retention and operator cleanup of unreferenced assets. Do not bridge staging and production media buckets or secrets.
8. **Business setup:** Provision the first individual admin with `npm run auth:provision-admin` and `SHOPBD_ADMIN_EMAIL` in a controlled job; pipe the password from a protected prompt/secret manager. Rotate any legacy demo admins. Never enable `SHOPBD_ALLOW_DEMO_SEED` on a deployment. Ensure Admin → Settings contains real contact, policy, branding and BDT settings; map delivery districts and fees, verify COD and minimum order and test courier/support runbooks. There is **no courier API or online payment provider**; fulfillment/status/COD collection are staff-operated.
9. **Operations:** Schedule `npm run auth:cleanup` with the runtime DB role (expiry only). Keep backups encrypted and tested; cap service and upload requests at ingress, configure alert owner/on-call, verify edge/no-store and separate secrets/recovery for storage, DB and app. Retest auth and SEO after any origin or proxy change.
